# Почему первый заход в ЛК с новыми данными долгий

## Коротко: стратегия действительно пересчитывается заново — даже если админ её уже сгенерировал

Готовый снапшот в базе есть, но код считает его «протухшим» и на первом заходе пациента запускает генерацию заново, синхронно, с ожиданием ответа ИИ.

## Что именно проверено

1. **Правило инвалидации кеша по дате публикации отчёта.**
   В `compute-health-strategy` снапшот принимается, только если он создан **позже** `report_documents.published_at`. Данные из базы:
   - `a.s.prokhanov@yandex.ru` — снапшот от 23.07, отчёт переопубликован 07.08 09:56 → кеш отброшен;
   - `svetlanamineeva88@gmail.com` — снапшот от 10.07, отчёт переопубликован 07.08 09:57 → кеш отброшен.
   То есть любая (даже косметическая) перепубликация отчёта врачом обесценивает уже посчитанную админом стратегию.

2. **Дополнительные условия отбраковки.** Снапшот также отбрасывается, если пусты `roadmap` / `key_biomarkers` / `expectations` или роадмап «старого формата». В базе такие есть (`chagin@gmail.com`, `alina@mail.ru`, `lovetoevery1@gmail.com`) — у них при каждом заходе будет полная генерация.

3. **Несовпадение Health Index.** Проверка «HI снапшота == HI анализа» — у `alina@mail.ru` 91 против 86, снапшот всегда невалиден.

4. **Сколько это стоит по времени.** По логам ИИ-шлюза вызовы `google/gemini-2.5-flash` из этой функции идут **19–42 секунды** (до 26k входных токенов). Плюс сбор контекста из ~10 таблиц.

5. **Всё это время страница показывает пустой скелетон** — `HealthStrategy` ждёт `await generate(false)` до снятия `loading`, поэтому не видно ни возраста, ни Health Index, ни назначений, хотя они уже загружены.

6. **Никто не прогревает кеш заранее.** `compute-health-strategy` вызывается только из UI: страница стратегии и админский пересчёт/публикация. После публикации отчёта фонового пересчёта нет — первый зашедший пациент и оплачивает генерацию.

7. **Вторичные потери (секунды).** На странице 4 последовательные волны запросов; самая тяжёлая тянет 2 анализа со всеми `analysis_values` и 20+ колонками справочника, плюс отдельный лишний запрос «все анализы».

## Что предлагаю сделать

**A. Прогрев после публикации отчёта.**
При публикации/переопубликации отчёта сразу запускать `compute-health-strategy` в фоне (`EdgeRuntime.waitUntil`, без ожидания). К заходу пациента снапшот уже свежий.

**B. Не выбрасывать стратегию из-за переиздания отчёта.**
Инвалидировать кеш по дате публикации только если реально изменились данные, влияющие на стратегию (новый анализ, изменённый Health Index / значения биомаркеров), а не при любом сохранении отчёта.

**C. Показывать предыдущую стратегию, пока считается новая.**
Если свежего снапшота нет, но есть прошлый — рисуем его сразу с плашкой «Обновляем стратегию по новым данным…» и подменяем по готовности. Пустого скелетона на 30 секунд больше нет.

**D. Постепенная отрисовка.**
Возраст, Health Index, биомаркеры, назначения показываем сразу; скелетон оставляем только на ИИ-блоках (траектория, дорожная карта, ожидания).

**E. Ускорить запросы.**
Слить 4 волны в одну параллельную, урезать колонки биомаркеров, убрать дублирующий запрос «все анализы».

**F. Защита от гонок.**
Блокировка «расчёт уже идёт», чтобы одновременный заход пациента и врача не запускал две генерации.

## Технические детали

- `supabase/functions/compute-health-strategy/index.ts`, условия кеша — строки ~220–237 (`cacheNewerThanPublication`, `cacheMatchesLatestHealthModel`, `hasLegacyRoadmap`); один вызов `ai.gateway.lovable.dev` (`google/gemini-2.5-flash`).
- `src/pages/HealthStrategy.tsx` — `load()` ждёт `await generate(false)`; последовательные запросы ~140–200.
- Точка прогрева — серверная публикация отчёта (`publish_report_document` / поток `ReportV2Editor`).

Порядок: A+B (убирают ожидание почти полностью) → C → D → E → F.
