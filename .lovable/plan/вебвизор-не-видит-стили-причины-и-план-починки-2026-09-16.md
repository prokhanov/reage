# Вебвизор не видит стили: причины и план починки

## Что говорит Яндекс

- Вебвизор сохраняет HTML страницы в момент визита, а файлы стилей подгружает по ссылкам отдельно. Если файла по ссылке уже нет или он отдаётся с неподходящим `Content-Type`, запись показывается «голой» ([1](https://yandex.ru/support/metrica/ru/webvisor/requirements)).
- Отдельно Яндекс рекомендует хэш в имени CSS-файла, чтобы к записи подтягивался именно тот стиль, который видел посетитель ([3](https://yandex.com/support/metrica/ru/troubleshooting/webvisor?lang=ru)).
- На практике частая причина — стили подключены не обычным тегом `<link rel="stylesheet">`, а через отложенную/скриптовую подмену: тогда Вебвизор их просто не забирает ([2](https://stackoverflow.com/questions/79078299/ya-webvisor-doesnt-see-css-styles)).

## Что именно у нас

Три совпадения с этими причинами:

1. Основной файл стилей после сборки подключается не обычной ссылкой, а «предзагрузкой с подменой» (оптимизация скорости первого экрана). Для браузера это работает, для Вебвизора выглядит как «стилей нет».
2. При каждом новом деплое старые файлы стилей с хэшем удаляются. Запись визита, снятая до деплоя и просмотренная после, уже не находит свой файл — стилей нет.
3. Наш веб-сервер отдаёт файлы без заголовка, разрешающего забирать их со стороннего домена. Для части загрузчиков Вебвизора это блокирует скачивание.

## План

### Шаг 1. Диагностика (без изменений на сайте)

- Проверить на продакшене отдачу CSS: код ответа, `Content-Type: text/css`, доступность по прямой ссылке из записи Вебвизора.
- Взять конкретную «сломанную» запись, достать из неё ссылку на стиль и проверить, жив ли файл (это отделит причину №2 от причины №1).

### Шаг 2. Вернуть обычную ссылку на стили, не теряя скорость

Оставляем инлайн критических стилей и отложенную загрузку как есть, но после полной загрузки страницы (в простое, уже из кэша, без сетевого запроса) добавляем в разметку нормальный тег стилей. Вебвизор видит обычную ссылку, скорость первого экрана не меняется.

### Шаг 3. Сохранять предыдущие сборки стилей

Настроить деплой так, чтобы файлы 2–3 последних сборок оставались на сервере. Это убирает «пропажу стилей» в записях, сделанных до выкладки, и заодно лечит редкие поломки у пользователей со старой закэшированной страницей.

### Шаг 4. Разрешить забирать статику со стороны

Добавить на отдачу файлов заголовок кросс-доменного доступа. Влияния на скорость и работу сайта нет.

### Шаг 5. Проверка

После выкладки: новый визит с включённым Вебвизором, просмотр записи, сверка внешнего вида; замер скорости первого экрана до/после, чтобы убедиться, что ничего не просело.

## Технические детали

- `vite.config.ts` → `beastiesPlugin` использует `preload: "swap"`: итоговый HTML содержит `<link rel="preload" as="style" onload="this.rel='stylesheet'">`. Добавить в `index.html` пост-load хук, который на `requestIdleCallback` вставляет `<link rel="stylesheet" href="<тот же /assets/*.css>">` (ресурс уже в кэше, повторной загрузки нет).
- `deploy/nginx/default.conf` → в `location ^~ /assets/` добавить `add_header Access-Control-Allow-Origin "*" always;` рядом с существующим `Cache-Control: immutable`.
- Ретеншн ассетов: при сборке Docker-образа копировать `assets/` предыдущего релиза (или вынести `/assets` в персистентный volume/CDN-бакет), чтобы старые хэшированные файлы не исчезали.
- Изменения не затрагивают Beasties-инлайн, ленивые чанки и текущую логику ретрая CSS.

## Про страницы чекапов

Стили на `/checkup/*` те же самые, что и на главной — отдельного файла стилей у чекапов нет, поэтому шаги 2–4 чинят записи Вебвизора сразу на всех страницах чекапов. Проверку в шаге 5 делаем в первую очередь на `/checkup/vitamins` и `/checkup/energy` (туда идёт реклама): визит, запись, сверка внешнего вида, отдельно — открытие корзины и модального окна с примером расшифровки.
