# Автоаккаунт после оплаты разового чекапа

## Аудит: возможно ли
Да, полностью. Подтверждение оплаты уже приходит от Робокассы на сервер (через api.reage.life → nginx/Fly → функция `robokassa-result`), там же сейчас создаются записи чекапов. Аккаунт создаём там же — только после проверенной подписи Робокассы, поэтому неоплаченные заказы аккаунт не создают. Через nginx/Coolify ничего нового проксировать не нужно: используются те же функции и тот же домен.

## Флоу

```text
Оплата → Робокасса шлёт подтверждение (сервер)
  ├─ подпись неверна / не оплачено → ничего не делаем
  └─ оплачено:
       1. Ищем аккаунт: по email → по телефону
       2a. Не найден → создаём аккаунт (email подтверждён, телефон без подтверждения,
           случайный пароль), письмо «Данные для входа»
       2b. Найден → привязываем заказ, пароль НЕ шлём
       3. Создаём карточки чекапов на этот аккаунт
Покупатель возвращается на страницу результата → ждёт, пока появятся карточки
  ├─ новый аккаунт → одноразовый вход → «Разовые чекапы»
  └─ существующий аккаунт → если уже залогинен, сразу «Разовые чекапы»;
     иначе экран «Заказ добавлен в ваш кабинет, войдите» (email подставлен)
```

## Подводные камни и решения

1. **Захват чужого аккаунта (главный риск).** Если автоматически логинить в уже существующий аккаунт, любой может ввести чужой email/телефон, оплатить копеечный чекап и попасть в чужие медицинские данные. Поэтому автовход — только в аккаунт, созданный этим же заказом. Для существующего — привязка заказа + обычный вход (или вход по ссылке из письма).
2. **Телефон занят другим аккаунтом, а email новый.** По вашему правилу — привязываем к аккаунту с этим телефоном, без пароля и без автовхода. Новый аккаунт не создаём (иначе два аккаунта с одним телефоном).
3. **Email и телефон принадлежат разным аккаунтам.** Приоритет у email.
4. **Робокасса может прислать подтверждение дважды / раньше возврата покупателя.** Создание аккаунта и карточек идемпотентно (по заказу); повторный вызов ничего не дублирует.
5. **Покупатель закрыл вкладку до возврата.** Аккаунт и письмо всё равно создаются сервером; войти можно по паролю из письма.
6. **Ссылка возврата перехвачена/переслана.** Одноразовый вход выдаётся только один раз, живёт ~15 минут и привязан к секретному ключу, сохранённому в браузере при оформлении заказа. Без этого ключа (другое устройство) — экран входа, пароль в письме.
7. **Подтверждение email.** Помечаем email подтверждённым: покупатель реально получил письмо с паролем, автоподтверждение в общих настройках не включаем.
8. **Пароль в письме.** Генерируем надёжный, в письме — рекомендация сменить его в профиле. Пароль в базе/логах не сохраняем.
9. **Письма и ссылки** — только через домен reage.life / api.reage.life (блокировки РКН).
10. **Профиль.** Заполняем ФИО, дату рождения, телефон из заказа; запускаются обычные приветственные триггеры (Telegram «новый пользователь», серии писем) — как при обычной регистрации.
11. **Партнёрская привязка** срабатывает уже по аккаунту — закрепление сохраняется.
12. **Тестовые оплаты** — тот же путь, чтобы можно было проверить без реальных денег.

## Что увидит покупатель
- Новый: после оплаты сразу оказывается в кабинете на «Разовые чекапы» со своим заказом и допродажей; на почте письмо с логином, паролем и ссылкой.
- Существующий: заказ появляется в его кабинете; если не залогинен — просьба войти.

## Технические детали
- `energy-create-payment`: генерирует случайный `claim_secret`, хранит его хэш в `energy_orders`, сам ключ отдаёт браузеру (localStorage).
- Миграция `energy_orders`: `claim_secret_hash`, `account_created boolean`, `auto_login_used_at`.
- `robokassa-result` (после проверки подписи и `paid`, до вставки `one_time_checkups`): поиск пользователя по email (admin API) → по нормализованному телефону в `profiles` → иначе `auth.admin.createUser({ email, password, email_confirm: true, user_metadata })`, upsert профиля с телефоном; записывает `user_id` и `account_created` в заказ. Для нового — шаблон письма `checkup-account-credentials` через `send-transactional-email` (idempotencyKey по заказу).
- Новая функция `energy-claim-session`: принимает `InvId` + `claim_secret`; если заказ оплачен, `account_created`, хэш совпал и `auto_login_used_at` пуст — `auth.admin.generateLink({ type: 'magiclink' })`, возвращает `token_hash`; клиент вызывает `supabase.auth.verifyOtp({ token_hash, type: 'magiclink' })`. Отметка использования ставится атомарно.
- `EnergyPaymentResult.tsx`: после paid — вызов claim → сессия → `/one-time-checkups?payment=success`; для существующего аккаунта без сессии — экран входа с подставленным email и редиректом обратно.
- Деплой: `energy-create-payment`, `robokassa-result`, `energy-order-status`, `energy-claim-session`, `send-transactional-email`. Правила nginx-белого списка: проверить, что путь `/functions/v1/energy-claim-session` проходит прокси (если список путей явный — добавить).
- Проверка: тестовая оплата для нового email, повторный callback, существующий email, занятый телефон, открытие ссылки возврата в другом браузере.
